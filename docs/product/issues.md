# Issues — rev 1

## ISSUE-01: Notification `overdue_task` bị tạo trùng khi Firestore emit nhiều snapshot liên tiếp
- **AC liên quan**: AC-02-2
- **Severity**: high
- **Status**: fixed
- **Cách fix**: `services/notifications.service.ts` — `createNotification(input, id?)` giờ luôn dùng `setDoc(..., { merge: true })` thay vì `addDoc`; khi có `id` truyền vào thì ghi vào doc id xác định thay vì auto-id. `app/dashboard/page.tsx` gọi `createNotification(input, \`overdue_task_${task.id}\`)`. Nhờ vậy dù effect chạy lại nhiều lần do nhiều snapshot liên tiếp (hoặc nhiều tab), mọi lần gọi cho cùng task đều ghi đè lên đúng 1 doc — không còn phụ thuộc vào việc đọc lại `notifications` qua closure để chống trùng, chống race kể cả cross-tab.
- **Mô tả**: Dedup effect trong `app/dashboard/page.tsx` (~dòng 109-135) chỉ depend `[overdueTasks]`, đọc `notifications` qua closure (có `eslint-disable-next-line react-hooks/exhaustive-deps`). Khi `tasks` emit nhiều snapshot liên tiếp (Firestore local-cache rồi server-ack) trước khi subscription `notifications` kịp phản ánh notification vừa ghi, effect chạy lại với `notifications` cũ → tạo `Notification` thứ 2 cho cùng `relatedTaskId`.
- **Bằng chứng**: QC xác nhận trực tiếp qua Firestore — `task-phoenix-1` có 2 notification `overdue_task` tạo cách nhau 1ms; 2 task QC seed thêm cũng bị trùng.
- **Bước tái hiện**: Có task quá hạn chưa từng có notification → load Dashboard → Firestore emit 2 snapshot tasks gần nhau → 2 notification `overdue_task` cho cùng task được tạo.
- **Gợi ý fix**: dedup nên chống race — ví dụ dùng ref/set in-memory đánh dấu "đang xử lý/đã xử lý" theo `taskId` ngay khi bắt đầu gọi `createNotification` (không đợi round-trip subscription), hoặc kiểm tra lại trong Firestore bằng query trước khi ghi (nếu cần chống trùng cross-tab/cross-session), hoặc constraint ở tầng ghi (doc id xác định = `overdue_task_<taskId>` thay vì auto-id, dùng `setDoc` để ghi đè thay vì `addDoc` tạo mới).

- **Severity**: high (blocker cho QC)
- **Status**: fixed
- **Cách fix**: thêm `signInAnon()` trong `services/auth.service.ts` (dùng `signInAnonymously` từ Firebase Auth, cùng pattern `signInWithGoogle`). Thêm nút "Continue as guest" trong `app/login/page.tsx` gọi hàm này song song với nút Google hiện có, không đổi luồng Google. Đã đọc kỹ `linkOrCreateUser` — không cần sửa: `firebaseUser.email` dùng `?? ""`, `displayName` dùng `?? email`, `photoURL` dùng `?? null`, đều đã xử lý `null`/`undefined` an toàn cho user ẩn danh (không có email/displayName thật), không crash.

Không thay đổi luồng Google hiện tại.
- **Lưu ý**: `linkOrCreateUser` (gọi khi sign-in) cần hoạt động đúng với `User` ẩn danh của Firebase (không có email/displayName thật) — kiểm tra không crash khi các field đó là `null`/`undefined`.

## ISSUE-04: Notification `overdue_task` trùng lặp còn tồn đọng trong Firestore từ trước khi fix ISS-01 (dữ liệu rác chưa dọn)
- **AC liên quan**: AC-02-2
- **Severity**: minor
- **Status**: closed
- **QC verify (vòng 3)**: Vào `/notifications` trên UI thực — `qc-task-overdue-5d`, `qc-task-overdue-1d`, `task-phoenix-1` mỗi task chỉ còn đúng 1 notification `overdue_task`, không còn cặp trùng nào. Không có console error.
- **Cách fix**: viết script one-off (`scripts/_cleanup-dup-overdue-notifications.ts`, dùng cùng cách kết nối Firestore REST API như `scripts/seed.ts`) để quét toàn bộ `notifications` collection, gom theo `relatedTaskId` cho `type === "overdue_task"`, giữ lại bản có doc id đúng format `overdue_task_<taskId>` (nếu có) hoặc bản `createdAt` cũ nhất, xoá các bản còn lại. Chạy script và kiểm tra trực tiếp Firestore (cả REST list lẫn `runQuery` structured query để loại trừ phân trang/cache): tại thời điểm chạy, `notifications` collection chỉ có 6 doc tổng, đúng 3 doc `type === "overdue_task"` — mỗi `relatedTaskId` (`qc-task-overdue-5d`, `qc-task-overdue-1d`, `task-phoenix-1`) chỉ còn đúng 1 bản, không phát hiện cặp trùng nào còn tồn tại nữa (script log "Deleted 0 duplicate" — dữ liệu rác mô tả trong issue đã không còn tại thời điểm fix, có thể đã được dọn/ghi đè giữa lúc QC ghi nhận issue và lúc fix chạy). Đã xoá file script khỏi repo sau khi chạy xong (one-off, không phải code lâu dài).
- **Mô tả**: Fix của ISS-01 (deterministic doc id `overdue_task_<taskId>` + `setDoc merge`) hoạt động đúng cho mọi notification được tạo **sau khi fix** — QC đã verify bằng 8+ lần reload Dashboard liên tiếp (kể cả dồn dập) trên nhiều task, không phát sinh trùng mới. Tuy nhiên, khi QC vòng 2 mở trang Notifications lần đầu, phát hiện 3 task (`qc-task-overdue-5d`, `qc-task-overdue-1d`, `task-phoenix-1`) mỗi task có **2** notification `overdue_task` với **doc id ngẫu nhiên kiểu `addDoc`** (ví dụ `ef4pBsf1rmzd1RIdg2yM`, `zyrgevhlc5KsOQm5QOrA` — không phải `overdue_task_<taskId>`), timestamp cách nhau vài trăm ms, được tạo **trước khi dev server hiện tại khởi động** (tức là dữ liệu tồn đọng từ lần chạy code cũ, có thể là chính lúc Developer/QC vòng 1 phát hiện ra ISS-01, trước khi fix được áp dụng). Dữ liệu rác này vẫn hiển thị trên trang Notifications thật, khiến PM thấy 2 thông báo giống hệt nhau cho cùng 1 task — vi phạm trực tiếp yêu cầu "tổng số notification cho task đó vẫn là 1" của AC-02-2 ở trạng thái hiện tại của hệ thống, dù root cause logic đã được fix.
- **Bằng chứng**: Query Firestore trực tiếp (`notifications` collection, `type == "overdue_task"`) tại thời điểm bắt đầu QC vòng 2 cho thấy 6 doc cho 3 `relatedTaskId` (2 doc/task), toàn bộ đều có `createdAt` sớm hơn thời điểm dev server phiên QC này khởi động (xác nhận qua `ps aux` so với timestamp `createdAt`).
- **Bước tái hiện**: Mở `/notifications` trên dữ liệu Firestore hiện tại (chưa dọn) → thấy "QC Overdue 5 days task đã quá hạn" xuất hiện 2 lần với cùng nội dung, cùng giờ tạo (chênh nhau ~200ms); tương tự cho "QC Overdue 1 day task" và "Rebuild pipeline caching layer".
- **Gợi ý fix**: chạy 1 lần migration/cleanup script xoá các doc `overdue_task` trùng `relatedTaskId` (giữ lại 1 bản, ưu tiên bản có doc id đúng format `overdue_task_<taskId>` nếu có, hoặc bản cũ nhất), không cần sửa code logic (logic hiện tại đã đúng cho notification mới).
